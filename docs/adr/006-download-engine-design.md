# ADR-006: تصميم محرك التحميل

**الحالة:** مقترح — ينتظر الموافقة
**التاريخ:** نوفمبر 2026

## السياق

محرك التحميل هو القلب التقني للمشروع. يجب تصميمه بحيث:
- يدعم تقسيم الملفات إلى أجزاء متوازية.
- يدعم الاستئناف.
- يتعامل مع أخطاء الشبكة بمرونة.
- يُبلِغ عن التقدم في الوقت الحقيقي.

## القرار

### البنية الأساسية

```
DownloadTask
├── معلومات: URL, file_name, save_path, total_size
├── حالة: pending | active | paused | completed | failed
├── أجزاء: Vec<Segment>
│   ├── Segment { start_byte, end_byte, downloaded, status }
│   ├── Segment { ... }
│   └── Segment { ... }
└── إحصائيات: speed, progress_percent, eta
```

### خوارزمية التقسيم

1. إرسال طلب `HEAD` للحصول على `Content-Length` و`Accept-Ranges`.
2. إذا دعم الخادم `Accept-Ranges: bytes`:
   - تقسيم الملف إلى `N` أجزاء (افتراضيًا N=8).
   - حجم كل جزء ≈ `Content-Length / N`.
   - الجزء الأخير يأخذ الباقي.
3. إذا لم يدعم Range أو الحجم غير معروف:
   - تحميل بدون تقسيم (اتصال واحد).

### التعامل مع الأخطاء

| الخطأ | الاستجابة |
|-------|----------|
| فشل اتصال جزء واحد | إعادة محاولة مع تأخير تصاعدي (1s, 2s, 4s, 8s…) حتى 5 محاولات |
| فشل كل الأجزاء | إيقاف التحميل مع رسالة خطأ + حفظ الحالة للاستئناف |
| رابط غير صالح (404, 403…) | إيقاف فوري مع رسالة خطأ واضحة |
| إعادة توجيه (301, 302) | تتبع التوجيه (حتى 10 مرات) |
| شهادة TLS غير صالحة | رفض الاتصال (لا يُتجاوز — أمان) |
| انقطاع الإنترنت الكامل | إيقاف مؤقت تلقائي + محاولة استئناف كل 30 ثانية |

### حساب السرعة والوقت المتبقي

- **السرعة:** متوسط متحرك (moving average) لآخر 3 ثوانٍ لتجنب التذبذب.
- **الوقت المتبقي:** `(البايتات المتبقية) / (السرعة الحالية)`.
- **التقدم:** `(مجموع ما حُمِّل من كل الأجزاء) / (الحجم الكلي) × 100`.

### أحداث التقدم

- تُرسل أحداث التقدم إلى الواجهة كل 500 مللي ثانية (لا كل بايت — لتجنب إغراق IPC).
- كل حدث يحتوي:
  ```
  {
    download_id: u64,
    progress_percent: f64,
    downloaded_bytes: u64,
    total_bytes: Option<u64>,
    speed_bytes_per_sec: u64,
    eta_seconds: Option<u64>,
    active_segments: u32,
    status: String
  }
  ```

### إدارة الملفات المؤقتة

- كل جزء يُكتب في ملف مؤقت منفصل (`.part.N`).
- عند اكتمال الجزء، يبقى الملف المؤقت.
- عند اكتمال كل الأجزاء، تُجمَّع في الملف النهائي وتُحذف الملفات المؤقتة.
- عند الاستئناف، يُقرأ حجم كل ملف مؤقت لمعرفة ما اكتمل.

### تقنيات Rust المستخدمة

| المكون | التقنية |
|--------|---------|
| async runtime | `tokio` مع multi-thread scheduler |
| HTTP client | `reqwest` مع `stream` feature |
| كتابة الملفات | `tokio::fs` للكتابة غير المتزامنة |
| التنسيق بين الأجزاء | `tokio::sync::mpsc` channels |
| حالة مشتركة | `Arc<Mutex<...>>` أو `tokio::sync::RwLock` |

> ⚠️ هذا تصميم أوّلي. التفاصيل ستُحدَّث عند كتابة الكود في المرحلتين 1 و2.

## العواقب

- تصميم الأجزاء المنفصلة يُعقّد الكود لكنه ضروري للاستئناف والتسريع.
- يجب اختبار التعامل مع كل حالة خطأ بشكل مستقل.
- أحداث التقدم كل 500ms قد تحتاج ضبطًا بناءً على الأداء الفعلي.
